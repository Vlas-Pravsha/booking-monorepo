# Booking System MWP

Цей документ описує фактичний стан продукту в репозиторії та цільовий `MWP`-сценарій, який треба добудувати.

`MWP` у цьому контексті:

- сайт ресторану є головною продуктовою поверхнею;
- налаштування ресторану і сайту мають жити в адмінці;
- адмінка має поєднувати конфігурацію сайту, статистику й аналітику;
- сайт генерується з онбордингу;
- AI має знаходити дні та слоти з найменшим попитом і генерувати знижки для заповнення залу.

## 1. Продуктова ідея

Продукт допомагає ресторану не просто приймати бронювання, а керувати попитом.

Базова логіка така:

1. Власник реєструється.
2. Проходить онбординг і заповнює модель ресторану.
3. На основі онбордингу генерується tenant-сайт ресторану.
4. Гості заходять на цей сайт, знайомляться з рестораном і залишають бронювання.
5. Система збирає дані про попит.
6. AI аналізує слабкі дні/слоти й формує знижки.
7. Ці знижки показуються гостям прямо на tenant-сайті, щоб стимулювати бронювання в непопулярний час.
8. Адмінка показує статистику, динаміку попиту, завантаження і результативність знижок.

## 2. Ролі в продукті

### Власник ресторану

- реєструється та входить у систему;
- проходить онбординг;
- формує публічну вітрину ресторану;
- керує доменом, контентом, графіком, столами та правилами бронювання;
- дивиться статистику й AI-рекомендації.

### Гість

- заходить на domain/tenant-сайт конкретного ресторану;
- переглядає опис, фото, меню, відгуки, контакти;
- бачить доступні знижки або вигідні часові слоти;
- залишає бронювання;
- отримує підтвердження й далі взаємодіє з рестораном.

### AI-модуль

- аналізує історію бронювань;
- знаходить найслабші дні та часові проміжки;
- пропонує або автоматично створює знижки;
- передає ці знижки на tenant-сайт;
- дозволяє оцінювати, чи спрацювала акція.

## 3. Ключова бізнес-логіка MWP

### 3.1. Tenant-first модель

- у кожного ресторану є власний `domain`;
- tenant-сайт є основною публічною поверхнею бренду для гостей;
- налаштування ресторану та сайту виконуються в адмінці;
- адмінка є центром конфігурації контенту, домену, графіка, столів і правил бронювання.

### 3.2. Онбординг як генератор сайту

- онбординг збирає базові дані про ресторан;
- ці дані формують публічну сторінку ресторану;
- після завершення онбордингу власник уже має готовий domain-site;
- повторне редагування цієї ж моделі має відбуватися в адмінці.

### 3.3. Бронювання як частина вітрини

- бронювання не є окремим продуктом від сайту;
- гість спочатку бачить бренд і пропозицію ресторану;
- далі переходить до вибору дати, часу, кількості гостей і контактів;
- якщо є AI-знижка, вона має бути видимою в момент вибору слота.

### 3.4. AI discount engine

- вхідні дані: бронювання по днях, слотах, кількості гостей, статусах, виручці;
- мета: знайти дні та часові проміжки з найменшим навантаженням;
- результат: створити рекомендацію або автогенеровану знижку;
- вихід: знижка відображається на tenant-сайті у відповідних слотах;
- аналітика: власник бачить, чи знижка підняла кількість бронювань і завантаження.

### 3.5. Адмінка як центр керування і аналітики

Цільова роль адмінки в MWP:

- налаштування сайту й ресторану;
- редагування контенту сайту;
- керування доменом, графіком, столами і правилами бронювання;
- дашборд по бронюваннях;
- завантаженість по днях і годинах;
- слабкі слоти;
- статистика по знижках;
- динаміка бронювань і гостей.

Нецільова роль адмінки в MWP:

- бути публічною поверхнею для гостей;
- замінювати tenant-site як брендований сайт ресторану.

## 7. User Journey MWP

### 7.1. Journey власника ресторану

1. Власник заходить на маркетинговий сайт.
2. Реєструється.
3. Потрапляє в онбординг.
4. Заповнює назву, домен, опис, контакти, години роботи, столи, контент.
5. Після завершення отримує готовий tenant-site.
6. Далі заходить в адмінку і керує сайтом та рестораном звідти.
7. Дивиться статистику в адмінці.
8. Отримує AI-інсайти про слабкі дні/слоти.
9. Підтверджує або редагує знижки.
10. Відстежує, чи дали знижки приріст бронювань.

### 7.2. Journey гостя

1. Гість відкриває сайт конкретного ресторану.
2. Переглядає опис, меню, фото, відгуки та контакти.
3. Бачить вигідні дні або часові слоти, якщо AI активував знижку.
4. Обирає дату, час і кількість гостей.
5. Залишає контактні дані.
6. Створює бронювання.
7. Отримує підтвердження або подальшу комунікацію від ресторану.

### 7.3. Journey AI

1. Система накопичує бронювання.
2. Групує їх по днях тижня, датах, слотах і кількості гостей.
3. Визначає найменш популярні дні/слоти.
4. Розраховує, де доцільно дати знижку.
5. Створює промо-пропозицію.
6. Віддає її на tenant-site.
7. Збирає результати: перегляди, бронювання, приріст.
8. Оновлює наступні рекомендації.

## 8. Бізнес-правила, які мають бути в MWP

### 8.1. Домен і тенантність

- один власник має один ресторан у поточній моделі;
- кожен ресторан має унікальний домен;
- дані одного ресторану не повинні бути видимі іншому;
- tenant-site завжди читає дані лише свого `domain`.

### 8.2. Генерація сайту

- сайт не збирається вручну розробником;
- сайт формується з моделі ресторану, яку власник заповнив сам;
- онбординг створює мінімально життєздатну версію сайту;
- подальші зміни цієї моделі миттєво змінюють tenant-site.

### 8.3. Бронювання

- бронювання можна створити лише в робочі години ресторану;
- бронювання має враховувати `averageDuration`;
- бронювання має враховувати наявні столи й місткість;
- слот не можна показувати доступним, якщо під нього немає валідного столу;
- після створення бронювання дані мають з'являтися в аналітиці.

### 8.4. AI і знижки

- AI не повинен генерувати знижки навмання;
- знижки будуються на історичних даних;
- AI має пояснювати, чому конкретний день або слот визнаний слабким;
- власник повинен бачити рекомендацію, а не лише кінцевий відсоток;
- у системі має бути видно ефект від знижки.

## 10. Definition of Done для MWP

MWP можна вважати готовим, коли виконуються всі умови нижче:

- власник реєструється і проходить онбординг без участі менеджера;
- після онбордингу одразу отримує робочий tenant-site;
- усі налаштування сайту й ресторану робляться в адмінці;
- гість може створити реальне бронювання з цього сайту;
- система вміє визначати слабкі дні/слоти;
- система показує знижки для таких слотів;
- адмінка дає конфігурацію сайту, аналітику й ефект від AI-знижок;
- дані по бронюваннях, клієнтах, столах і ресторану ізольовані між tenant-ами.

У репозиторії вже є сильний фундамент для MWP:

## 13. Технічний контекст репозиторію

Цей проєкт — pnpm + Turborepo monorepo.

Актуальні runtime apps і packages:

- `apps/application` — Next.js 16 frontend для marketing, auth, onboarding, tenant site і admin UI;
- `apps/backend` — Hono REST API для auth, restaurant owner data, admin data, public reservations, contact requests і persistence;
- `packages/contracts` — shared Zod contracts і TypeScript types для frontend/backend синхронізації.

Поточна архітектура:

```text
Browser / root domain / admin subdomain / tenant subdomain
  -> Next.js application with proxy-based routing
  -> shared API client + TanStack Query / Redux
  -> Hono REST API
  -> contracts/zod + domain functions + Prisma
  -> database/cache/storage providers
```

Важливі шляхи:

- frontend routes/views: `apps/application/src/app`, `views`, `widgets`, `features`, `entities`, `shared`;
- backend routes/domains: `apps/backend/src/routes`, `domains`, `contracts`, `core`, `lib`;
- Prisma schema: `apps/backend/prisma/schema.prisma`;
- generated Prisma client: `apps/backend/src/generated/prisma` — вручну не редагувати;
- roadmap задач: `tasks/README.md`.

## 14. Development Commands

З root директорії:

```bash
pnpm install

pnpm check-types
pnpm build
```

App-specific validation:

```bash
pnpm --filter @booking/contracts check-types
```

Для full-stack задач треба перевіряти contracts, backend і frontend разом.

## 15. Contracts-First Rule

Кожна API-зміна має йти в такому порядку:

```text
packages/contracts
  -> apps/backend/src/contracts + routes + domains
  -> apps/application shared api + entities/features/views
  -> validation
```

Це критично для MWP, бо frontend і backend уже мають реальні API-backed flows. Якщо змінити тільки UI або тільки backend, легко отримати contract drift.
